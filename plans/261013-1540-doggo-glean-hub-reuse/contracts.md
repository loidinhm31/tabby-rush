# Doggo contracts — Hub auth + opt-in strict per-record sync
Date:2026-10-13. Selected by user after feasibility review. Planning only; exact Kotlin declarations freeze in02. [Architecture](architecture.md) · [Decisions](reports/design-decisions.md) · [Feasibility](reports/strong-sync-feasibility.md).

## 1. Scope, origin and isolation
Reuse existing Hub authentication, app schema registry, dual auth and Mongo. Only Doggo opts into new `syncMode:"strict-v1"`; existing apps retain legacy wire/storage/clients unchanged. No Worker/D1, OAuth, new password backend, receipt ledger, ordered feed or snapshot protocol. Strict client never falls back to legacy sync.
`HubConfig={canonicalOrigin,appId:"doggo",appApiKey,buildMode}`; no base path/query/fragment/userinfo. API prefix `/api/v1`. Release only approved HTTPS origin; debug additionally exact `http://localhost:3000`, `http://127.0.0.1:3000`, `http://10.0.2.2:3000`;15001 only separately approved debug config. No redirects/TLS bypass/credential forwarding. Connection10s/request20s, no automatic transport/POST retries.
AccountKey=full SHA256 of unambiguously length-framed canonical origin and exact server userId; not email. Origin/app change requires guarded leave. Actual app key excluded from source/docs/logs; packaged key extractable identification, not human authorization. No admin/JWT-signing/Mongo/deploy secret packaged. Other apps' keys never reused.

## 2. Existing authentication and onboarding
All existing bodies JSON camelCase; successful handlers200. Auth routes need no app key; `/me` and access requests bearer only. Password transient, never trimmed/stored/logged; login email trim+lowercase matches registration normalization.
| Method / relative path | Request | Response consumed |
|---|---|---|
|POST `/auth/register`|`{username,email,password}`|`{userId,accessToken,refreshToken}`|
|POST `/auth/login`|`{email,password}`|`{userId,accessToken,refreshToken,apps,isAdmin}`|
|POST `/auth/refresh`|`{refreshToken}`|`{accessToken,refreshToken}`|
|GET `/auth/me`|bearer|`{userId,username,email,apps,isAdmin,notificationsAllowed,timezone?,createdAt}`|
|POST `/apps/access-requests`|bearer;`{appId:"doggo",message?}`|AccessRequestInfo|
|GET `/apps/access-requests/me`|bearer|AccessRequestInfo[]|
AccessRequestInfo=`{id,userId,username,appId,message?,status,createdAt,updatedAt}`. Filter doggo, choose latest createdAt (list unordered); pending/approved/rejected known, unknown non-granted. Only current `/me.apps` proves cooperative-client grant; approved-without-grant is admin-pending. After grant approval refresh once/relogin to update JWT apps claim. New signup without grant is not an empty authorized todo account.
Registration validation remains server authority: username UTF8 bytes3..32 and alphanumeric/underscore/hyphen, password UTF8 bytes8..128, basic email check. Native UI may help, not silently impose stale character-count rules. Verify `/me.userId` matches securely persisted login identity before bootstrap.
Access-request POST/GET errors including duplicate pending can be401. POST failure -> one own-list reconciliation; failing list -> bounded `/me` diagnosis, never recursive list or blind refresh/resubmit. No native admin grant/password reset/account deletion/browser-token import flows. Admin login allowed with warning recommending non-admin account; stored admin JWT remains privileged even without admin UI.

## 3. Refresh and authorization errors
Observed Hub access HS2566h; refresh random32bytes/hashed30days, revoke old then separately mint successor. No OIDC/issuer-audience/JWKS/token-family assumption. Grant removal may not invalidate issued JWT until expiry; Doggo checks current `/me` before each online round but cannot enforce malicious-client immediate revocation.
One single-flight refresh shared by foreground/worker. Atomically persist entire successor bundle before releasing waiters. Any failed/uncertain post-dispatch refresh, including404/500 after consumption, conservatively requires reauth; accepts extra prompts instead of replay loops. Successful successor with vault failure remains memory-only for persistence retry; pause background work and durably mark credential-persistence-pending outside bundle. Restart without successor ->ReauthRequired.04 emits safe persistence-state callback;05 owns durable metadata, no concrete cross-lane dependency.
Sync401 can mean invalid JWT, missing grant or wrong key. At most one refresh/recovery per operation then `/me`: invalid identity->ReauthRequired, absent doggo->AccessPending, valid identity+grant with continuing401->AuthorizationUnresolved/pause/operator recovery. No generic403 grant assumption. HTTP auth layer NEVER replays a push; coordinator owns retry of frozen strict operation. Network/429 backoff with jitter/Retry-After, no English-error parsing/raw HTML display. Current server error envelopes may be non-JSON.
Logout is local-only; no invented revoke route, no refresh-and-discard imitation. Other apps/devices remain signed in; copied issued tokens may remain valid. User explicitly accepted this boundary.

## 4. Schema registration, immutable mode and namespace
New admin-only POST `/api/v1/strict-apps` accepts this payload; existing POST `/apps` remains legacy unchanged. Old binaries return404/405 instead of silently registering a legacy app. Read-back remains mandatory:
```json
{"appId":"doggo","syncMode":"strict-v1","schema":{"todos":{"columns":[{"name":"id","type":"string","nullable":false},{"name":"title","type":"string","nullable":false},{"name":"completed","type":"boolean","nullable":false},{"name":"createdAt","type":"integer","nullable":false}],"primaryKey":"id"}}}
```
Strict registration only accepts appId `[a-z0-9-]{1,40}`, exact personal-todos schema/no sharing/no notificationEvents. Persist mode/strictEpoch as optional strings parsed at gates: absent mode legacy; unknown fails only that app, not list_apps. New code rejects ALL schema/sharing/mode updates for strict apps. Strict service uses fixed validated todo policy; altered registry tables from an old binary pause admission rather than changing semantics. Keep existing legacy register signature/callers/behavior; add real `register_strict_app` and dedicated admin handler.
Strict registration generates lowercase UUIDv4 epoch. Fixed todos storage uses intrinsic `_id=userId+\":\"+rowId` (exact24hex Hub subject,canonical UUID); no droppable secondary index is the uniqueness boundary. Create ordinary uncapped collection with simple/absent default collation,no custom validator/no TTL index,standard `_id` index and owner/table/row scan index. Verify exact options/index specifications BEFORE publishing registry LAST and admitting writes. Admission cached per app+epoch,failures affect only that app (not Hub initialize). Partial setup never admits unindexed/unknown namespace; operator retry inspects orphan setup,never overwrites an existing registration/key. GET `/apps/doggo` must echo mode+strictEpoch. One-time key private custody; no recovery/rotation endpoint.

Before any collection handle/use, push/pull validate canonical epoch equals active registry strictEpoch; mismatch409 epochMismatch,forged epoch creates no collection. Bootstrap reads active epoch and admitted namespace. Capture validated request namespace; never redirect in-flight request to a later epoch. Legacy-only router guard rejects any present mode with non401 protocol error; existing apps with absent mode unchanged. Legacy direct writers/cleanup/notification use old namespace and cannot reach strict rows. No automatic namespace import. Operator collection/index drops after admission are outside intact-storage guarantee and require maintenance/readmission.
Fetch active strictEpoch and validate current strict schema on EVERY bootstrap/push/pull using authoritative primary/majority registry read on replicas,primary on standalone;cache admission specs only,never epoch/schema authority. Oldepoch409 after rotation,newnamespace503 until admitted.03 read-only operator binary `strong_sync_admission` invokes SAME Rust validator on exact inactive candidate namespace before publication (protected operatorenv);public strong routes never access inactive epoch. Existing update_schema predicate requires syncMode absent;matched0 distinguishes notfound/strictrejection,legacy behavior preserved.

## 5. Data and operation identity
Todo id=rowId canonical lowercase UUIDv4. Title trims explicit Unicode White_Space (`0009-000D,0020,0085,00A0,1680,2000-200A,2028,2029,202F,205F,3000`), then1..200 Unicode scalar values; reject malformed surrogates/internal C0/DEL. No normalization/case folding. completed boolean; createdAt stable UTC epoch-ms integer0..9007199254740991, device time sorts UI only. UI order createdAt desc then id desc; whole local projection counts/filter, lazy paged rendering.
Server revision integer1..9007199254740991, server assigned only; expectedRevision0 means create, otherwise exact base. Delete data canonical `{}`. Strict server validates envelope AND Doggo data policy; existing schema validator alone is insufficient. Unknown mutation fields rejected to avoid digest ambiguity; forward-compatible response fields ignored.
Operation freezes `{opId,epoch,tableName:"todos",rowId,kind:create|update|delete,expectedRevision,data}`. opId canonical lowercase UUIDv4,reject aliases. client localRevision distinct from server revision; persist normalized frozen fields and resend them after restart,never recompute from editor. Same operation never changes base/data/kind/id; explicit reapply new user-authorized operation after remote review. One unresolved per-row operation dispatched FIFO; successors retained separately.
Digest=SHA256 over canonical identity/request encoding.02/03 freeze cross-language vectors: unsigned32 big-endian byte-length then UTF8 for domain `strict-v1`,appId,exact authenticated userId,epoch,table,rowId,opId,kind; unsigned64 big-endian expectedRevision; create/update adds length-prefixedUTF8 id/title,one byte completed0|1,unsigned64BE createdAt;delete no data fields. No map-order/floating-point/locale dependence. Server returns computed digest; mismatch blocks protocol. Update must preserve existing createdAt or return invalidRecord before mutation. Invalid normalization/schema never stored as lastOp; titles never logged,digest not encryption.

## 6. Strict HTTP surface and structured outcomes
New POST `/sync/:app_id/strong/bootstrap`, `/push`, `/pull`, relative `/api/v1`; JSON+Bearer+dedicated X-API-Key+X-App-Id. Existing dual auth supplies userId; no body user authority. Routes inherit sync rate/body/plugin gates; no new public credentials. `/bootstrap` returns `{protocol:"strict-v1",appId,epoch,tables:["todos"]}`. Mode unsupported/unknown route->ProtocolIncompatible, no legacy fallback or destructive cache reset.
Push body=`{protocol:"strict-v1",epoch,operations:[frozenOperation...]}` <=100 unique rowIds and256KiB serialized. Server rejects duplicate same-row entries/envelope failure before writes; validated records otherwise independently applied, not batch transaction. Return matching protocol/epoch and per-operation `{opId,rowId,digest,status,acceptedRevision?,current?}`. Status machine codes: accepted,replayed,revisionConflict,missingRecord,deletedRecord,opIdReuse,invalidRecord,retryableFailure. English strings are not behavior. A missing/undecodable result is unresolved, never inferred from a count.
Only accepted/replayed with exact account+epoch+opId+digest and expectedRevision+1 acknowledges captured local revision. Stale response cannot clear successor. A pull row/payload match NEVER acknowledges an operation. For apparent rejected response after previous uncertain delivery, mismatch may mean original succeeded then was superseded: local UnknownSuperseded, not proof of rejection. Retain intent and require explicit review.
Non2xx/transport/cancel/process death after dispatch ->UNCERTAIN until explicit acceptance/rejection interpretation. Safe retries reuse identical frozen request;409 epoch/reset and426 unsupported protocol pause;401 bounded auth recovery, not POST transport retry. Record retryableFailure backs off; after3 failed rounds block automatic retries visibly with manual recovery, never discard. Invalid data/protocol pauses sync with actionable repair while preserving local editing.
Strict-local request error type emits `{error,code}` with409 epochMismatch,426 protocolUnsupported/notStrictApp,400 invalidRequest,503 notAdmitted; does not change legacy SyncError/DTOs. Genuine auth middleware errors retain existing401 mapping. Any retryableFailure,including concern failure after applied write or confirmation timeout,is MAYBE applied,retains UNCERTAIN. `current` contains revision/deleted only,no lastOp. Protocol conflict decisions never branch on English.
Client mapping:409epochMismatch->ResetRequired;426 or404/405oldbinary->ProtocolIncompatible;503notAdmitted->bounded transient backoff with outbox preserved;400invalidRequest->protocol pause distinct from per-record invalidRecord. No automatic credential refresh for these strict-local codes.

## 7. Atomic strict write and replay rules
Create expected0 uses insert_one with revision1 and `{lastOp:{opId,digest,acceptedRevision:1}}`; duplicate identity reread->exact latest replay or conflict, never overwrite. Update/delete filters authenticated identity+epoch/table/row+revision==expectedRevision+deleted:false and no upsert; atomically set canonical data/deleted/lastOp and increment server revision1. Missing non-create rejected; existing tombstone cannot be recreated/implicitly undeleted. Overflow rejected before mutation. Any accepted mutation changes revision; equal-version ABA from client-selected revisions is removed.
Exact lastOp ID+digest match confirms replay without another logical effect. Same latest ID/different digest->opIdReuse. Superseded lastOp cannot prove historical outcome; immutable old expectedRevision cannot apply again. Guarantee covers frozen requests, not arbitrary historical opId reuse with a new base/payload (no global receipt ledger).
Deterministic record handling: validate envelope/data; latest lastOp exact match->durable confirmation/replayed; latest ID mismatch digest->opIdReuse; absent non-create->missingRecord; create-existing or wrong revision->revisionConflict; matching-base tombstone->deletedRecord; otherwise attempt conditional mutation. After lost CAS reread and classify,never pretend accepted. Optional expected+1 inference deliberately omitted: after prior uncertain delivery retain conservative UnknownSuperseded on superseded state. Remote tombstone can show deletion satisfied and offer explicit discard,NOT auto-clear or receipt.
Replay acknowledgement requires REAL metadata-only conditional write matching identity+revision+lastOp+digest,setting fresh confirmationNonce with configured journaled concern. Success means matched_count1 with acknowledged concern,not modified_count/no-op/visibility. Every replay path,including duplicate-create reread and concern-error recovery,uses this. Invariant when lastOp exists:acceptedRevision==row.revision;violation pauses corruption. Failed match due to successor->conflict/unknown;timeout uncertain. Nonce not logical revision/data/DTO. Initial acceptance also waits configured concern. Imported recovery rows may have lastOp=null and never supply replay evidence.
Standalone policy explicit `{w:1,j:true}` with primary reads; no disk-loss redundancy/HA promise. Replica policy `{w:"majority",j:true}` plus appropriate primary majority reads. Topology/journal/version and actual indexes verified before admission; no global defaults changed for other apps. Read visibility alone cannot establish durable acceptance. No multi-document transactions required for these per-row rules.

## 8. Tombstones, full scans and promotion
Delete permanently retains identity/revision/deleted/lastOp/confirmation metadata with empty data; no deleted title retained. No TTL/physical purge/legacy restore on strict storage. Lifetime distinct-row count grows; user accepted compact permanent markers. No fixed retention promise or automatic GC. Explicit CopyAsNew creates new UUID; normal update never restores.
No compaction job: delete already atomically writes canonical empty data; retain identity/revision metadata for epoch lifetime. Repeated different delete against tombstone does not bump revision. No quota/finite-history guarantee invented.
Pull body=`{protocol:"strict-v1",epoch,tableName:"todos",cursor:null|opaque,batchSize:100}`. Reply includes protocol/epoch,records,cursor,hasMore. Records=`{tableName,rowId,revision,deleted,data}`; private confirmation metadata not exposed. Server scans authenticated user+epoch+table by immutable rowId with simple binary collation, strict-after; limit+1 only for hasMore, cursor from last RETURNED record. Cursor encodes protocol/app/owner/epoch/table/afterRowId, all checked against authenticated scope; no cursor field grants authority. Client echoes server cursor only, detects mismatch/nonprogress and bounds page memory.
Full scan starts null every round, includes compact tombstones, stages to SQLite and promotes only at terminal page. Not snapshot: behind-cursor new rows/after-read edits wait another round. Pace serial pages/honor429; two10k-row scans roughly200 requests before push. No global-freshness claim or timestamp cursor.
Promotion per row retains higher confirmed revision over stale scan; equal revision with differing logical data/deleted is ProtocolIncompatible. Overlay pending/uncertain/drafts. Track scan-start known identities/revisions: missing identity confirmed BEFORE scan start within same epoch is consistency/reset error, not deletion/recreate; identities confirmed after start remain retained. Corrupt/incomplete scan preserves old base; restart from null. Successful later full scan after quiescence converges under intact storage/epoch and eventual successful requests.
Epoch change/mismatch on any page discards staging and pauses ResetRequired before promotion. Replica scan reads primary/majority. Cursor requires no new signing secret: authenticated scope checks always override decoded fields.

Fresh external UUID epoch/newnamespace+indexes;copy approved rowId/data/deleted with revision1,lastOp=null,canonical empty tombstones. Empty reset only explicit separate option. Validate complete counts/schema and run03 actual admission helper on inactive candidate before journaled registry strictEpoch CAS old->new. PRE-CAS failures leave oldpointer. Cannot recover absent-backup writes;never reopen rolledbackepoch or replay oldoutbox into new.

Existing apps' data/protocol not migrated. No runtime automatic fallback to weaker semantics; infeasibility triggers reported plan revision before deployment.

## 10. Local persistence, scheduling and account leave
Room KMP+BundledSQLiteDriver; logical stores server_base,outbox,editor_drafts,scan_staging,account_sync_meta. Per-origin/user OS-private DB; no SQLCipher claim/no credentials in SQLite. Explicit migrations, no destructive fallback. Atomic edit/draft+outbox before saved-local success. Coalesce never-dispatched edits; unsent create-delete may cancel. Persist DISPATCHING before socket; restart/cancel ->UNCERTAIN. Frozen revisions protected from late ack; online round validates identity/grant/epoch,scans,pushes eligible operations,scans again.
Android same-process WorkManager unique network one-shot + periodic15min best effort; shared coordinator/refresh locks, AccountKey/generation only in WorkData. Drain/re-enqueue edits during active work (KEEP cannot lose wakeup), recover commit/enqueue gap on startup. Desktop only while app open. No exact timing/force-stop guarantee.
Vault: Android Keystore AES-GCM fresh nonce+atomic wrapped bundle; Linux Secret Service/no plaintext fallback; Windows user-scoped DPAPI+restricted ACL+atomic file. Bundle opaque/redacted. Backup/device transfer excludes DB/credentials/session/wipe metadata. Desktop single-process profile lock prevents duplicate refresh. Locked vault/error never silently wipes data. Established account restarts offline; first login/switch online. Known denied grant quarantines pending data, not deletes.
Leave guard counts drafts,pending,uncertain,conflict,UnknownSuperseded and old-epoch review. Sync-and-leave only after resolution/accepted queue/final scan; cancel restores exact prior state; discard warns local-only loss and possible remote commit. Confirmed leave: freeze edits/scheduling ->persist new generation+wipe marker OUTSIDE DB ->cancel unique+periodic work and await terminal WorkInfo+owned callbacks/requests ->close Room ->delete DB/WAL/SHM/staging/cache/drafts ->remove vault+identity ->clear marker. Marker failure aborts before deletion; deletion failure fail-closed/retry, never opens B. Startup marker check before DB/vault, cancel leftover work and finish wipe. Remote request may still commit; wipe is not forensic erase or remote rollback.
