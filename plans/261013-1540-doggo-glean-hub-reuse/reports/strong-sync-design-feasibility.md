# Strong-sync design feasibility — Doggo only

## Verdict and decision boundary
- **Feasible, conditionally:** A gives strict stale-write rejection, at-most-one logical effect per frozen mutation, and no implicit resurrection without Mongo transactions. It does **not** recover every historical operation outcome or provide a snapshot/feed.
- Recommend A **only if** visible `UnknownSuperseded` review and eventual reconciliation are acceptable. If every uncertain operation must remain causally identifiable after arbitrary later edits, choose B with durable receipts; A cannot meet that requirement.
- Neither means universal losslessness/exactly-once. Database rollback, storage destruction, explicit user discard and authorized reset are separate failure/recovery boundaries. No recommendation to revise approved phases until this trade-off is accepted; otherwise retain current protocol with its documented limits.
- Scope: one Doggo protocol cutover, not a replacement for existing Hub applications. Admin-login warning and local-only logout unchanged; no auth/logout work.

## A — strict revision CAS + permanent markers + stable-key full scans
### Mutation and replay contract
1. Doggo-owned strong storage, immutable identity `(appId, authenticatedUserId, epoch, tableName, rowId)`. Only `todos`, canonical UUID keys, no sharing. Required unique identity index and scan index verified before enabling traffic.
2. Durable client operation freezes `opId`, expected server revision, mutation kind and normalized payload. Digest covers identity/epoch, expected revision, kind and canonical payload; client local revision is separate. Account/user comes from existing dual-auth context, never a body-supplied authority.
3. New create: expected revision 0, insert-only, server revision 1. Duplicate key triggers reread/replay-or-conflict, never overwrite. Edit/delete: exact expected-revision predicate with no upsert; server alone increments revision by 1. Missing non-create is rejected. Missing assumptions, overflow and client-selected server revision are rejected.
4. Atomically store payload/deleted state, revision and `lastOp={opId,digest,acceptedRevision}` in the same row. Exact latest-op identity+digest match returns its stored acceptance without another logical revision. Same latest ID with different digest is a protocol error. Payload equality alone never acknowledges a dispatched operation.
5. Replay acceptance requires durability, not just visibility: replica-set majority read with journal-backed majority history, or a conditional **real metadata-only confirmation write** matching identity/revision/lastOp/digest, setting a fresh internal nonce with the configured journaled write concern. No-op update is not a journal barrier; failed match/write-concern error remains unresolved. Standalone uses the confirmation-write path; logical revision/data/lastOp do not change.
6. After a successor replaces `lastOp`, retry still carries its old expected revision and cannot apply. If previous delivery was uncertain, mismatch means `UnknownSuperseded`, not proof the original failed. Retain original intent/history; show remote state plus explicit discard/review/copy-as-new choices. No automatic rebase or retry with a new opId/base.
7. A deliberate reapply after viewing the new base is a **new user-authorized mutation**, not replay. Operation IDs/payloads never retarget. Last-op storage cannot detect arbitrary historical ID reuse with a different base: guarantee is for immutable frozen requests, not global ID-ledger deduplication.
8. Per-row FIFO, one uncertain/in-flight mutation before a successor dispatch; durable pending overlay and captured local revision ensure an old ack cannot clear a newer edit. Other devices remain concurrent. Batches have independent per-record outcomes, not all-or-nothing semantics; no external side-effect delivery claim.

### Deletion, scans and visible semantics
- Deletion permanently retains identity/revision/deleted/lastOp and confirmation metadata; empty payload permitted. Compaction removes retained user content only, never the anti-resurrection/replay marker. No physical identity removal/recreation in the epoch, including via cleanup jobs. Storage grows with distinct IDs ever created, not merely live todos.
- Ordinary edit cannot undelete a tombstone. No Doggo restore endpoint is needed: explicit copy creates a new UUID. If restore is later authorized, it must be an explicit new revision-CAS mutation, never legacy restore or create-on-existing-ID.
- Page by immutable `(tableName,rowId)` within owner+epoch with simple/binary collation and strict-after cursor; fixed todos table can use rowId alone. Include compact tombstones. Return at most100 rows, derive `hasMore` from limit+1 and cursor from the last **returned** row. Cursor binds protocol/app/owner/epoch/table; reject mismatch/non-progress, no timestamp order dependency.
- These are **full scans, not snapshots**. A key inserted behind a page cursor waits until the next round; an already-read row can change before completion. Fixed row keys do not move on edits, eliminating timestamp-induced repeats/order ambiguity, not concurrent-write staleness.
- Stage and promote only complete scans; retain higher confirmed per-row revisions over older scan values and reject inconsistent same-revision **logical** state. Wire tombstones always use canonical empty data; confirmation nonce/internal metadata are excluded from DTOs/equality, so compaction/reconfirmation are not logical changes. Preserve pending/uncertain/drafts. Never treat absence/payload equality as a receipt. Absence diagnoses corruption/reset only for identities confirmed before scan start in the same epoch, with appropriate read consistency; later confirmations/creations remain retained and reconcile next round, never silently delete/recreate.
- UI: saved locally/pending; accepted revision; last completed reconciliation; explicit conflict/unknown/reset states. No global-freshness badge or claim all devices are current. Later full scan after quiescence converges, assuming intact epoch/storage and eventual successful requests.

### Epoch/reset and durability boundaries
- App-scoped random epoch is mandatory in every request, response, cursor and storage key. Bootstrap obtains protocol+epoch without inventing a new auth flow. A reset rotates epoch and uses a fresh immutable namespace; never recycle epoch/revisions/row identities inside an epoch.
- Capture namespace from the **request epoch**; never silently reroute an old operation into the currently active epoch. Stale epoch => explicit reset-required state, retained old intents/drafts, new base bootstrap; no automatic old-outbox rebase. Responses from another epoch cannot clear current work.
- Epoch isolation prevents late old requests mutating the new namespace; **it does not prevent an already-running request committing in the old namespace after reset**. Separate active-epoch check then row write is not atomic. Stronger reset-vs-acceptance ordering needs coordinated maintenance/quiescence or B's transactionally written epoch/head fence.
- Operator backup restore/rollback must block traffic, retire all old server writers, assign a fresh epoch from authority outside the stale backup, bootstrap restored content under that epoch, then reopen. It cannot recover data absent from the backup. Reopening a rolled-back epoch invalidates A's at-most-once/monotone-revision assumptions.
- No replica set required for row safety. Journaled standalone `{w:1,j:true}` supports the declared crash-durability boundary but no disk-loss redundancy or HA. On replicas require explicit `{w:"majority",j:true}` and appropriate majority reads; do not change global Mongo defaults for other apps. Write-concern timeout/transport loss always means unknown, not rollback/rejection.

## B — permanent receipts + monotone feed + real snapshot bootstrap
- Same strict revision CAS/account/epoch boundaries, but transaction atomically writes row/tombstone, unique receipt `(app,user,epoch,opId)` with immutable digest/result, immutable full post-image feed entry and serialized per-account head increment. Receipt binds row too; reuse with another payload/row is rejected.
- Every successful transaction writes the shared account head, so sequence allocation cannot overtake another account-local commit. Aborts roll back counter/row/receipt/feed together; do not allocate sequence outside the transaction. Per-account contention is an accepted cost for small personal datasets.
- Exact receipt resolves lost acknowledgment **after later edits/deletion**, without reapplying the mutation; feed orders accepted changes. Store terminal rejection receipts too if promising stable outcomes for rejected requests. Driver transaction/commit retries must respect unknown commit and receipt identity, not issue a new logical mutation.
- Concrete snapshot mechanism: Mongo5.0+ snapshot `find` reads at one explicit `atClusterTime=T`, including account head `H` at T, then all row pages at the same T in a non-causally-consistent snapshot-read context. Bootstrap token binds T/H/owner/epoch; only after atomic local promotion start feed `seq>H`.
- Separate majority reads or UUID scans cannot substitute. Snapshot-history expiry/timeouts => discard staging and restart bootstrap with new T/H, never advance a partial checkpoint. History window must support maximum dataset/page duration; driver/command support must be established. Do not keep a multi-minute HTTP bootstrap inside the default minute-lifetime transaction.
- Feed pagination uses immutable sequence with a bound committed head. Apply feed data and cursor in one local transaction; include deleted events. Permanent receipts+tombstones and initially retained feed avoid unsafe TTL shortcuts. If pruning is required, add explicit earliest-sequence/bootstrap-retention fences; slow clients below the floor must reset, never silently skip events.
- Finite receipt retention forfeits unbounded historical outcome lookup unless device leases/ack frontiers or an equivalent accepted-operation horizon reject old requests before receipt GC. This is additional protocol/ops work, not “TTL receipts imply exactly-once.”
- Reset actually modifies a **shared app-epoch fence** that every mutation transaction also conditionally modifies (e.g. increment fence serial with expected active epoch), in addition to its per-account head. Reading app epoch while writing a different account head is insufficient. This provides reset/write conflict ordering but adds app-wide write contention. Old transactions conflict or belong wholly to the retired namespace. Backup rollback still needs new externally authorized epoch; retained durable history is not universal losslessness.
- Requires supported replica set (FCV>=4.0 for transactions; >=5.0 for the chosen outside-transaction snapshot approach), journaled majority durability, verified driver sessions/readConcern support, provisioned indexes and operational backup/failover/history-window policies. Live topology unknown: **conditional feasibility, not deployment-ready approval**.
