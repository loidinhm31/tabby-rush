# Android Glance and quiet deadline notification research

Research date: 2026-10-16. Planning evidence only; exact dependency graph and device behavior unverified.

## Findings

- **Stable Glance candidate:** AndroidX release notes list `androidx.glance:glance` and `glance-appwidget` **1.2.0** as stable, released 2026-08-26; 1.3.0 is alpha. Use aligned `1.2.0` artifacts as the implementation candidate, not alpha/RC APIs. The 1.2 alpha notes moved Glance AppWidget compileSdk to 35; beta notes moved minSdk to 23. TabbyRush minSdk 26 is above that floor. **Not verified:** exact Glance 1.2.0 + Kotlin 2.1.10 + Compose Multiplatform 1.7.3/Android plugin compatibility. Compile and resolve conflicts before selecting the candidate.
- Glance is a RemoteViews-backed widget DSL, not a way to embed ordinary Compose UI. Its UI guide documents responsive sizing and `LazyColumn`; interactions support callbacks and activity launches. Use Glance-native list, checkbox/action controls, and Add/Open activity entry points; select a responsive size mode from launcher-provided sizes. Do not promise arbitrary nested scrolling; test real launcher scrolling and supported sizes.
- Launcher widget IDs are system/host-owned instances, not Activity/ViewModel state. Register a `GlanceAppWidgetReceiver`; enumerate installed IDs with `GlanceAppWidgetManager` and refresh all instances after relevant state changes. Render each update from cold-safe persisted current-account state. A process/activity restart must not be a prerequisite for hydration. Avoid account-specific widget configuration/state; on logout/account replacement update all surviving instances to an empty/signed-out projection and ensure wipe recovery clears old content. Test launcher restore, force-stop/restart, account switch, and OS-retained stale RemoteViews.
- Use explicit, immutable intents/actions with unique identity (component/action plus distinct request code or data URI); carry account generation/account ID and task ID, then re-check them against the ready current account before mutation. A stale action must no-op, never open another account runtime. `FLAG_IMMUTABLE` prevents the sender from changing intent fields; use `FLAG_UPDATE_CURRENT` only when updating the same intended operation. Give task Complete/Open distinct identities. Complete must set `completed=true`, not toggle. Widget callback and notification action paths both need this fence.
- Android 13+ requires `POST_NOTIFICATIONS` runtime permission for ordinary notifications. Request only after an explicit in-app opt-in and rationale; denial is a supported unavailable state, not a failure or reason to nag. Keep widget/task operations working. Use a dedicated low-importance, no-sound/no-vibration channel; channel importance is user-controlled and cannot be programmatically raised after the user lowers/blocks it. Check runtime permission/app notification enablement and channel importance before posting; offer a user-directed Settings path, never silently recreate a channel under another ID to evade a block. Keep this opt-in separate from reminder-alert settings.
- Android 14/API 34 allows users to dismiss ongoing notifications. `setOngoing(true)` is not a persistence guarantee. Provide a delete intent and persist suppression before/when dismissal is processed; never immediately repost the same selected task in response to that dismissal. Conservative reset: suppress only the exact selection key `(account generation, task ID, persisted deadline value/type/time-zone semantics)`; while it remains selected, refreshes and rollover wakeups do not repost. Clear suppression when that key changes/disappears, on explicit opt-out, or on a deliberate user re-enable of this surface. If dismissed notification is not removed on a particular system path, test it and do not infer a delete callback.
- Refresh selection after successful local mutation, sync completion, account transition, startup/recovery, and supported date/time/time-zone changes. Use supported inexact background work (e.g. WorkManager) as a best-effort reconciliation path; periodic WorkManager has a 15-minute minimum and is inexact, not a midnight alarm. Register appropriate system time/date/time-zone change handling for a running process and reconcile on next safe app/worker start. No exact-alarm permission or foreground service for this static surface; force-stop/doze/OEM scheduling means no exact rollover or immediate remote-sync guarantee.

## Implementation recommendations

- Build a single current-account projection from committed persisted task state plus saved pending local changes. Ignore unsubmitted editor drafts. Do not gate eligibility on reminder-enabled state or reuse a reminder scheduler predicate that does. Exclude completed/removed/no-deadline tasks. Resolve deadline instants/date-only boundaries through existing persisted schedule/time-zone semantics, never display strings. Select oldest overdue first; otherwise earliest upcoming; task ID deterministic tie-break. No result => cancel the one task notification. Recompute after any task/account/sync change and time-boundary trigger.
- Give the task notification its own channel, stable notification ID, action identities, and private lock-screen content with a generic public version. Post/update one item only; selection replacement is an ordinary update. Complete/Open must validate account generation and current task state. Notification disabled, permission denied, or channel blocked must not affect widget availability.
- Ask permission only when the user opts into the separate “next deadline” surface, explain ongoing notification behavior and device Settings control, then request runtime permission where required. Persist feature opt-in separately from OS permission/channel state; distinguish opted-out, permission-denied, app-disabled, and channel-disabled states for UX, without claiming the notification is available.

## Validation risks and gates

- **Build gate:** compile the exact Glance 1.2.0/Kotlin 2.1.10/Compose 1.7.3 configuration with minSdk 26, compileSdk 35; inspect resolved AndroidX/Compose versions. Release-channel status and minSdk do not prove compiler/plugin compatibility.
- **Device gate:** test responsive small/large launcher sizes, scrolling, completion callback, Add/Open, host restore, process death, force-stop/relaunch, stale action after logout/account switch/wipe, and content clearing after account replacement.
- **Notification gate:** API 32 and API 33+ permission states; channel blocked/low importance; lock-screen privacy; API 34+ swipe dismissal/delete-intent behavior; suppression across refresh, task change, deadline edit, selected-task replacement, opt-out/re-enable; duplicate/stale action delivery.
- **Scheduling gate:** task completion/edit/sync, tied deadlines, overdue ordering, date-only/time-zone semantics, system date/time/time-zone changes, delayed inexact work and force-stop. Test that dismissing never produces a repost loop. Do not claim precise rollover.
