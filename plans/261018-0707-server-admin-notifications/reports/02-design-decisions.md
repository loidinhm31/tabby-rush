## Selected design
1. **App identity:** actual Hub app ID `tabby-rush`; Android Firebase application ID `dev.tabbyrush.android`; existing Windows AUMID `dev.tabbyrush.desktop`. Never silently substitute `tabbyrush` or `TabbyRush.App`.
2. **Atomic acceptance:** bounded immutable parent document includes canonical content, complete resolved recipient snapshot, digest/idempotency identity, expiresAt and recoverable pending materialization state. Journaled insert before 202 response. No multi-document transaction prerequisite. Materialize recipient rows and device work with deterministic IDs/upserts, then mark parent complete only after verification. Parent recovery is authoritative if child writes partially succeed.
3. **Bounds proposed for contract:** title 1..200 Unicode scalars + <=800 UTF-8 bytes; body 1..4000 scalars + <=16KiB; <=500 total resolved recipients for selected/all/admin modes; reject larger audience (do not silently truncate/chunk audience resolution after acceptance). <=64KiB intake request; serialized parent <=1MiB. App/message routing strings and device inputs bounded separately. These are conservative internal-deployment limits, not Firebase limits on message content (content never goes in push).
4. **Audience confirmation:** server preview returns current eligible recipient IDs/count plus opaque bounded snapshot identity/digest and expiry. Send must confirm exact preview membership, with current role/grant recheck; if eligibility changed, reject with audienceChanged and request reconfirmation. Users joining later never enter accepted snapshot. Preview is not accepted message/dispatch intent. Freeze exact route/schema and snapshot storage or signed representation in contract; do not make independent UI/backend guesses.
5. **Dispatch:** server-owned leased worker in same process. Parent and child lease CAS include owner+fencing token/generation; reclaim expired processing as well as pending/retryable jobs; final updates match fencing identity. Network timeout shorter than lease or lease renew/recheck; bounded concurrency, bounded retry attempts/backoff, expiry stops work. Recheck current user grant, membership, expiration, device owner and binding version immediately before send. Persist per-target outcome; provider acceptance never means device receipt. No SSE listener means skipped hint, not a never-ending retry job.
6. **No acceptance/child gap:** at every write boundary, a pending/reclaimable parent or durable child must own remaining work. Crash/restart tests must kill real server against standalone Mongo. Inbox is canonical recipient membership+parent content; acceptance may return pending until materialization, with worker convergence documented. No accidental zero-recipient success: reject empty resolved audience.
7. **Device binding:** authenticated owner, install identity independent of account, app, FCM token, monotonic binding fence, stale unregister and invalid-token retirement match exact owner+version+token. Cross-account rebinding must reject delayed old register, even if its request first reaches server after switch; server read-current-version alone is insufficient. Contract must define persisted client install operation generation + server CAS/recovery (or stronger install credential) and retry/lost-response semantics. Unauthenticated caller cannot steal binding by guessed install ID; never accept caller userId as owner.
8. **Client cache:** bounded in-memory remote inbox/controller state only; no durable offline content/read queue, no Room/task schema migration. Offline UI explicitly says unavailable/stale and does not open cached content without authenticated server reauthorization. Clear all content/navigation/dedup state on leave/revocation/generation change and filter expired content at render/time transitions. Server durable inbox survives reconnect/restart. Reading while offline cannot claim server acknowledgement.
9. **Read convergence:** idempotent monotonic mark-read (set first readAt only), current recipient authorization, mutation returns canonical read state. Multiple devices refresh unread and visible pages on hints/reconnect/foreground/bounded reconciliation; creation-only cursor must not pretend to capture read-state changes. Specify stable keyset pagination `(createdAt,id)` and how full refresh merges/removes expired items without cursor skips.
10. **SSE:** dedicated app-scoped authenticated minimal announcement hints. Reuse existing recipient-scoped channel primitive, not `broadcast_to_app`, and preserve old producer envelope/routes. Freeze subscribe acknowledgement/baseline, buffer hints during baseline, silent reconcile, server-time/sequence based live classification (not client wall-clock). Historical/replayed/delayed hints must not cause toast storm. Inbox pagination cursor != stream offset; `Last-Event-ID` alone is not durable recovery. Grant revocation and JWT expiry terminate or revalidate stream; stale callbacks are fenced client-side.
11. **Android:** native Firebase Messaging SDK with fixed generic notification+data payload. Exactly one alert path: background SDK auto-render, foreground Firebase callback local generic post; SSE/reconcile never generates Android OS alerts. Same key names cold/warm, remote group/channel distinct from reminders. No FCM token deletion prerequisite on logout: best-effort versioned unbind, local cleanup always proceeds. Late generic OS auto-render accepted; click fetches via current auth and unauthorized target falls back to safe inbox, never displays old account content.
12. **Windows:** choose small owned C++/WinRT bridge DLL loaded via JNA, real toast Activated callback marshalled into application UI dispatcher, existing AUMID, installed per-user MSI shortcut identity and deterministic remote-specific groups/tags. Own native source, CMake/build/package integration and clean-host proof. No invented size estimate, PowerShell notification, AWT fallback, or claim existing JNA stub is functional. Running-process click is required; cold receive after quit is excluded. Existing OS notification clicked after quit must be explicitly handled safely or no longer actionable; never imply new incoming live delivery.
13. **Linux:** persistent D-Bus connection and action listener, scoped native ID→opaque routing map, daemon owner-change/reconnect cleanup, real `actions` capability gating. Missing actions does not guarantee default-click behavior. Show capability limitation with in-app inbox access; supported daemon click must pass real smoke. Preserve no-tray visible recovery path. Do not unconditionally force focus on Wayland or claim window manager permits it.
14. **Privacy/policy:** content-only authenticated inbox; FCM/SSE generic/opaque only, tokens/service credentials redacted; separate remote policy and OS capability from email `notificationsAllowed`. No new user preference product feature implied; show remote inbox availability and platform permission independently. Local reminders/sticky/task sync unchanged; lifecycle bug correction only where necessary to safely quiesce remote work.

## Corrections to researcher-01 (do not copy uncritically)
- Example claim filter omits expired `processing`; crash recovery requires it.
- Global sparse idempotency key index should become explicit unique `(appId,senderId,idempotencyKey)` with immutable digest; define retention/reuse rules, no accidental cross-admin collision.
- Recipient resolution after acceptance for all/admin violates snapshot requirement; bound and embed full recipient snapshot before acknowledgment.
- Background notification payloads are rendered without client callback; no client dedup guarantee. At-least-once ambiguous retries may duplicate generic alerts.
- `INVALID_ARGUMENT` alone does not prove invalid token; retire only detailed token-specific code after payload validity established. `SENDER_ID_MISMATCH` must be classified separately from generic project/credential failure.
- Do not inject credential JSON strings into arbitrary env/logs; prefer read-only secret file/ADC and no client credentials.

## Corrections to researcher-02 (do not copy uncritically)
- Suggested route names and userId request field were illustrative, not approved protocol. Freeze one route/DTO contract and derive owner exclusively from authenticated claims/current DB.
- AppVersion is not a binding version. Firebase install token callback may happen signed out; keep token privately until current authenticated bind.
- Foreground generic alert is required when permitted, not optional low-priority display based on active screen.
- FCM extra names must match, not `announcementId` on server vs `announcement_id` in activity.
- Do not use local `createdAt >= connectionStartTime` or assume UUID message IDs are monotonic; use server handshake/baseline ordering.
- Clear only remote-owned notification groups/IDs, never global history or local reminder alerts.
- Preserve existing Windows AUMID. No unmeasured DLL size and no displayMessage fallback; native activation is a real delivery gate.

## Parallel execution architecture
- Gate A: exact cross-language contracts, storage algorithms, error/state semantics, ownership manifest and dependency/build prerequisites.
- Wave B: disjoint backend storage/routes, FCM transport, React admin, shared core, shared UI, Linux adapter, Windows native adapter, operations files. Compile against Gate A contracts; runtime integration waits for real components. Keep per-module behavior tests with module owners.
- Wave C: Android runtime and desktop host integration, each owning all existing host/composition files on its platform. If native adapter needs central desktop build edits, reserve those files to native Windows owner, not host owner.
- Wave D: live cross-repo end-to-end acceptance, security regression and docs reconciliation; owns only separate smoke/evidence/docs files, cannot re-edit earlier owners' source/tests. Defects go to original owner, not conflicting blanket integration edits.
- Phase independence means self-contained implementation against frozen contracts, **not** false absence of dependencies. Explicit DAG and dependency matrix distinguish implementation start gates and runtime acceptance gates.
- Plan stays pending / 0%; no implementation is authorized or credited.
