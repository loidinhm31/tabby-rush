# Frozen implementation contract — admin announcements

Date 2026-10-18 · P2 · pending · 0%. This specifies future implementation, not deployed behavior. Authority: [decisions](02-design-decisions.md), [brainstorm](../../reports/brainstorm-261018-0228-server-admin-notifications.md). Research examples are superseded here. Changes require one coordinated contract amendment before consumers change; no independent endpoint guesses.

## 1. Identity, encoding, bounds and authority
- Hub application ID exactly `tabby-rush`; Android package `dev.tabbyrush.android`; Windows AUMID `dev.tabbyrush.desktop`.
- JSON camelCase, UTF-8; UTC RFC3339 timestamps with millisecond precision; IDs lowercase canonical UUIDv4 except existing Hub user IDs (24 lowercase hexadecimal Mongo ObjectId strings). UUIDs are opaque, **not monotonic**. Unknown request fields reject. Display plain text, never HTML/Markdown interpretation or external-link execution.
- Intake <=65,536 bytes; title trimmed once, 1..200 Unicode scalars and <=800 UTF-8 bytes; body normalize CRLF to LF and trim outer whitespace once, 1..4,000 scalars and <=16,384 bytes. Reject NUL and invalid UTF-8. Exact normalization repeated by server; confirmation displays normalized content. Canonical parent BSON <=1,048,576 bytes before insert.
- `selected` 1..500 unique user IDs; resolve at most 501 to detect overflow in **every** audience mode. Accept 1..500 resolved recipients, never truncate. selected IDs without grant are reported excluded; unknown IDs indistinguishable from ineligible. Admin audience = current `users.isAdmin == true` intersect `users.apps` containing `tabby-rush`; all = every current granted user; selected = requested IDs intersect grant. Admin sender must be current DB admin, but need not personally have receiver grant.
- JWT signature/expiry establishes identity only. Every admin route reads current DB sender role. Every receiver/device/stream route reads current DB user and grant; stream rechecks every 15s and before hints. Inbox/detail/read also check immutable membership. `notificationsAllowed` remains the existing email gate; it does not gate this feature. OS permission/capability is reported independently; no new preference or task-sync schema.
- Bearer header only; never access tokens in URLs, cookies substituted for bearer, redirects or app API-key bypass. Receiver routes are BEARER_ONLY, not strict-sync dual-auth. HTTPS on validated canonical origin; existing explicit debug loopback exception only. Responses `Cache-Control: no-store`; proxy buffering disabled for SSE.

## 3. Preview confirmation and idempotent intake algorithm
1. Preview resolves full sorted deduplicated set from current users; enforce bound including selected input bound. Persist immutable preview with sender/app/spec/digest/recipientIds/createdAt/expiresAt using acknowledged write; preview is not dispatch intent.
2. Admin normalizes content, freezes `{previewId,audienceDigest,title,body}`, generates one UUID idempotency key **before** submit. Disable edits/submission while outcome unknown. Keep key+frozen body in current browser sessionStorage for bounded recovery, clear on logout; no access tokens stored there. Deadline90days; warn before exposing draft on shared browser, clear on owner mismatch.
3. Server first queries existing `(appId,senderId,key)` before inspecting current preview expiry/membership. Same canonical request digest returns202 original Acceptance (`replayed:true`), no re-resolution; conflicting body returns409. Digest canonical field-order JSON with normalized title/body and preview identity/digest (not mutable role data).
4. For genuinely new key, validate preview ownership/app/digest/expiry; resolve current same audience and compare full set/digest. Changed recipient identity or admin membership ->409 audienceChanged; do not silently replace preview. No zero-recipient success. DB eligibility can change immediately after check; this is validation-at-acceptance, not a Mongo transaction with user mutations. Dispatch/read always reauthorize current grant. Persist accepted immutable snapshot precisely as confirmed.
5. Under process broker admission lock reserve `acceptanceOrdinal` and current `acceptanceEpoch` (section7), then perform bounded parent insert with `w:1,j:true` on standalone or configured majority+j on replica set. Mongo write timeout5s; no fire-and-forget. Ordinal may be wasted; never reused. Return202 only after successful acknowledged journaled insert; unknown write outcome ->503 and instruct same-key recovery. Unique conflict rereads existing record/digest. No multi-document transactions.
6. Parent creationTime set once on insert; expiresAt=createdAt+90*24h. Key idempotency identity is retained in parent until this expiry; at/after expiry and before TTL return410 without content. After physical deletion, old-key dedup cannot be promised: clients MUST NOT reuse UUID keys or retry past original90day window. Fresh action always new key. No tombstone requirement for messages beyond retention; install tombstones are different.
7. Unknown submission: UI GET by-idempotency then retries exact POST/key if404, preserving original preview/body even if preview has since expired. Existing accepted record wins before preview validation. If truly uncommitted and preview expired/changed, show definitive rejection and require fresh preview+explicit confirmation+new key. Never generate a replacement message just because request timed out. Sender losing admin cannot recover history until restored; UI says permission lost, does not resend as another admin.
Canonical digest encoding is UTF-8 JSON without whitespace, fixed field order and ordinary JSON escaping: audience hash over `{appId,audience,recipientIds}`, normalized audience `{mode,userIds}` (userIds omitted unless selected, sorted/deduplicated); request hash over `{previewId,audienceDigest,title,body}`. SHA-256 lowercase hex prefixed `sha256:`. Do not hash UI labels, timestamps or mutable roles. Vectors freeze non-ASCII/escaping behavior.

### Canonical inbox and read without materialization gaps
Canonical membership/content is **parent**, not child availability. Inbox list queries parent `recipientIds` and active expiresAt and joins readAt by deterministic inbox ID, default null until child exists. Detail and unread likewise derive active parents; unread counts those without nonnull readAt. PUT read upserts the same recipient row, `setOnInsert` identity/createdAt/expiresAt and atomic set readAt only if null/missing; never overwrite first readAt. Materializer uses `setOnInsert` and cannot erase read state. Read may initialize a row before fanout; it must not mark fanout complete. This avoids accepted-but-invisible or mark-read404 gaps. Bounded internal audience; aggregation+indexed parent lookup is adequate; no separate cursor event log.
PUT read executes journaled ensure-row `$setOnInsert`, then `updateOne` matching null/missing readAt to set serverNow once, then rereads canonical row. Unique races reread existing row. Crash before readAt update is unacknowledged and safe to retry; concurrent successful readers retain the first timestamp.

Inbox/sent pages descending `(createdAt,_id)`; strict predicate `createdAt < c.time OR (createdAt == c.time AND _id < c.id)` with UUID lexicographic bytes consistently encoded BSON subtype4. Cursor is base64url canonical JSON `{v:1,kind:"inbox"|"sent",appId,userScope,upperTime,upperId,afterTime,afterId}` + server HMAC; <=1KiB. Initial page fixes upperTime=serverNow and upperId=max UUID sentinel; continue with same upper bound and scope. Cursor is pagination only, not Last-Event-ID/read/live order. Cross-user/kind tampering ->400. New page1 refresh resets chain; never mix an old nextCursor with refreshed page1. Expired entries filtered on every page; ordering does not assume IDs track creation order.
Cursor wire format is `base64url(JSON) + "." + base64url(HMAC-SHA256(key, JSON-bytes))`; key derived by HMAC-SHA256(existing server JWT secret, fixed label `tabbyrush-announcement-cursor-v1`). JWT-secret rotation invalidates pagination (400 then restart page1), not inbox/read data. Golden vectors freeze JSON field order exactly as above and timestamp/UUID encoding.

## 5. Durable materialization, leases and provider outcomes
- Parent pending is durable responsibility for **all** snapshotted users until complete or expired. Worker every1s, parent concurrency1; recipients batches25, device sends max4. Parent+dispatch lease60s, renew every15s; FCM connect5s/total15s, DB operation5s. Fencing generation increments on each CAS claim.
- Claim `(pending OR retryable with nextAttemptAt<=now OR processing with leaseUntil<=now) AND expiresAt>now`. A pending job has leaseUntil epoch, nextAttemptAt creation time. Final/renew/checkpoint writes require `_id,leaseOwner,leaseGeneration,status:processing` and live lease. If renewal fails/expiry arrives, stop new I/O; cancel in-flight if possible, never accept stale completion. A network request already sent may remain ambiguous; no exactly-once guarantee.
- Persisted parent state pending|processing|retryable|complete|expired; dispatch state pending|processing|retryable|providerAccepted|hintPublished|failed|skipped|expired (hintPublished only SSE; providerAccepted only FCM). Inbox fanoutState pending|processing|complete; batch.materialized false->true only after verified upserts. Parent/dispatch leaseOwner UUID, leaseGeneration positive Int64, leaseUntil/server dates; pending/ready retryable claims require nextAttemptAt<=now, expired-processing claims require leaseUntil<=now. Terminal records never reclaimed.
- Recipient/batch progress also owns a lease triple (recipient uses fanoutLease* fields; batch uses lease*). Same60s/15s expiry/reclaim/renew/CAS rule; owner claims/renews child progress only while parent lease current, waits/reclaims expired prior child lease before resume, and every progress/final update matches that document's owner+generation+live lease. Parent uses materializationState=processing, dispatch uses status=processing, recipient uses fanoutState=processing. Materialized batch is terminal. Cross-document checks are not transactions: late immutable upserts are harmless, but no stale lease holder may commit progress/complete state.
- For each sorted recipient: upsert inbox identity preserving readAt; CAS initialize immutable `fanoutCutoffAt` to serverNow and cursor=null/batchIndex0. Query **current** bound Android installs for this owner/app with `boundAt<=cutoffAt`, `_id>cursor`, sorted `_id` ascending, page50. Every accepted bind/rotation sets boundAt=serverNow. Device eligibility is frozen incrementally at this per-recipient scan, not message acceptance: a registration accepted after message acceptance but before scan start can receive an alert; binds/rotations after cutoff never backfill this old message. A changed/unbound binding before enumeration may be skipped (canonical inbox remains), and a changed binding after snapshot fails pre-send fencing. No historical OS alert on later login/registration.
- Before advancing the scan, journal an immutable target-batch document keyed by nextBatchIndex, containing at most50 observed install/generation/tokenHash tuples plus from/next cursor and cutoff. On unique conflict reread winning batch, never replace it. Journal deterministic device dispatch upserts for every stored tuple; verify every child exists, then mark batch materialized and advance recipient cursor/index. Empty final page is persisted as `isFinal:true`; SSE dispatch is upserted independently. No send during this step. Crash before batch insert rescans current page; crash after insert reuses frozen batch. Checkpoints advance only after durable work, never replace recovery authority.
- Reclaim expired parent processing lease **before** any resume/finish. Stream all recipient batch records in index order; verify contiguous from/next cursor chain through final batch and every deterministic child ID, plus SSE child, before marking recipient/parent complete. No unbounded batch read or device array. Parent complete CAS matches current owner/generation/live lease only; stale child upserts are idempotent, stale completion cannot win. If expiry occurs first no dispatch; API hides parent immediately and cleanup removes derived batches/rows. Parent checkpoint is merely next recipient index, not sufficient proof of completion.
- Parent materialization retries indefinitely with bounded capped backoff while active (1s..5min), not permanent abandonment due to transient DB outage. Invalid persisted invariants place feature in operator-visible failure and retain pending responsibility, never report complete. Device dispatch max8 attempts, exponential full jitter base5s/cap1h;429 min60s and Retry-After if larger. Expiry always wins; retry time beyond expiry ->expired. SSE hint attempt is once after current grant check: no listener ->skipped(noActiveReceiver), not retry forever. Network publication ambiguity can repeat hints; client dedup suppresses within active connection.
- Immediately before provider send re-fetch active parent and member/current user grant, then install current owner+generation+tokenHash+bound state. Revoked or changed binding ->skipped. This is a point-in-time guard, not prevention of already-in-flight generic push after revocation. Dispatch never stores obsolete token secret in immutable target snapshot; resolve current token only after exact hash/fence match.
- FCM success ->providerAccepted with provider message name stored redacted/limited internally, not receipt. Timeout/reset/lease loss after send increments ambiguousAttempts and schedules retry when possible. `UNREGISTERED`, or detailed token-specific `INVALID_ARGUMENT` **after local payload validity established**, retires only `(appId,installId,ownerId,generation,tokenHash,state:bound)` matching target; state invalidToken preserves generation barrier. General INVALID_ARGUMENT ->payloadPermanentFailure, no device retirement. `SENDER_ID_MISMATCH` ->projectMismatch permanent target error, not generic invalidation; alert operator.401 evict OAuth cache and refresh once, then credential failure.403 auth/config permanent;429/500/503 honor Retry-After. Never log bearer/service key/token/private content.
- Disable worker/FCM does not delete accepted inbox or mark unsent targets delivered. Intake readiness requires the controls above; provider outage after acceptance is durable pending/failure, not lost acceptance. On provider pause, do not claim targets or consume attempts; resume/reclaim existing durable work with ordinary expiry checks. Feature config in phase11.

## 6. Android install ownership, fences and recovery
Header `X-Tabby-Install-Proof: <base64url 32 random bytes>` (43chars), TLS only and redacted in HTTP traces. ID random128bit UUIDv4 independent of account. Secret retained encrypted with Android Keystore in no-backup install storage; server stores only SHA-256 and constant-time compares. Proof is install possession plus authenticated user; not an authentication replacement. No caller userId allowed.

`BindRequest={operationGeneration:"17",platform:"android",token:"FCM opaque",appVersion:"1.0.0"}` token1..4096 UTF-8 bytes, version1..64ASCII. `UnbindRequest={operationGeneration:"18",expectedBindingGeneration:"17"}`. `BindingResult={installId,operationGeneration:"18",bindingGeneration:"18",state:"unbound",replayed:false}`; bound result state bound. `BindingStatus={installId,currentGeneration:"18",state:"unbound",ownedByCurrentUser:false,lastOperationMatchesCurrentUser:true}`; never returns another owner or token. `bindingGeneration` is last accepted operation generation; appVersion is **not** a fence.
BindingResult/BindingStatus state enum is bound|unbound|invalidToken. Exact command replay after token retirement returns current canonical invalidToken state, not fictitious rebound success; client obtains fresh token and reserves a newer generation. Retirement clears raw token/tokenHash while preserving owner, generation, secretHash and last-operation digest for fencing/replay. Unknown install GET is403; only authenticated first bind can create it.

Operation digest uses SHA-256 of fixed-order canonical JSON `{appId,installId,operationKind,operationGeneration,ownerId,platform,tokenHash,appVersion,expectedBindingGeneration}`; absent operation-specific values are null, numeric generation encoded decimal string, ownerId derived from current auth, tokenHash SHA-256 of exact token bytes. `operationKind` bind|unbind. Proof never included in digest/log; compare stored digest and authenticated lastOperationOwnerId for exact replay.
1. Installation initializes ID+secret+generation0 atomically. Unknown install can be created only by authenticated granted bind: unique insert with secretHash and positive generation, losing duplicate validates secret before anything else. Guessing ID cannot replace secret. Proof mismatch403. No read-current-version-then-unconditional-write.
2. Persist command+new generation under one install mutex **before** enqueue/network; command binds captured account generation/identity/token/digest. Increment for bind, token rotation, logout unbind and new-account bind. All callbacks enter same serializer; ignore old account callback, reserve newer generation for new intent. Persist immutable pending command across process crash only for install operations; no inbox content/read outbox. Encrypt command token; on startup discard old-account pending command and reserve a newer generation for current account (or defer until login).
3. Server accepts generation strictly greater than stored by CAS on stored generation+secretHash; bind derives owner from JWT/current DB. Same generation and same operationDigest+authenticated operation owner ->idempotent200; same generation different digest ->409 installOperationConflict; lower ->409 staleInstallOperation. Generation comparisons numeric, never lexical strings. No wrap; on exhaustion force fresh install identity and FCM token.
4. Unbind requires current owner==JWT user and expectedBindingGeneration==stored generation (or exact same-command replay), then sets owner/token null, state unbound, preserves secretHash/new generation/digest. CAS fails if any newer bind happened. Delayed old unbind cannot remove another owner even with higher proposed generation. Stale invalid-token cleanup matches exact fence/hash/owner. A strictly newer legitimate account bind may replace owner using install proof; delayed smaller bind never overwrites it, irrespective of HTTP arrival order.
5. Lost response retry **same generation and canonical operation body**. GET status with proof determines whether newer local intent needed, not permission to reuse a number. On stale response compare persisted local generation; never decrement or resurrect old account intent. A local switch reserves its new bind generation before scheduling it, so old delayed register/unbind is already lower than the switch command. Server cannot learn offline switch until request arrives; an old request that arrives first can temporarily bind old owner, but can never overwrite the later accepted new-generation binding. Generic in-flight push caveat remains.
6. Token uniqueness partial index `(appId,tokenHash)` for bound rows; another-install conflict409 tokenAlreadyBound, no stealing. Token rotation same install uses newer generation, atomically frees old token binding; retirement of old token cannot invalidate new one. Lost Keystore/cleared app data: never recover by guessed ID/proof; generate new identity and request Firebase deleteToken/getToken to obtain fresh token before bind if retained-token conflict occurs. This is recovery only, **not logout prerequisite**. Explicit install tombstones remain until administrative secure retirement, never automated TTL resetting fence. Access-restricted token storage/backup redaction required.
7. Logout locally invalidates runtime/account generation, cancels callbacks/content/nav, clears only remote-owned posted notifications, reserves best-effort unbind with expected binding and captured old auth. Wait bounded local cancellation/drain, not remote HTTP success. Offline/auth-expired unbind may remain unsent; never block cleanup or token deletion prerequisite. ## 7. SSE handshake, bounded recovery and live classification
Use existing per-user recipient channel primitive with **separate app-scoped minimal announcement channel map**; never `broadcast_to_app`, never legacy title/body envelope. Raw typed publication/subscription added without modifying old producer semantics. Broker has process UUID `streamEpoch`, monotonic u64 `acceptanceOrdinal` admission counter and monotonic `hintSequence` event counter. Parent records epoch/ordinal reserved before insert. Epoch is regenerated on restart; neither counter is UUID order or durable replay log.

Under short broker lock, register receiver and capture current acceptanceOrdinal + hintSequence; then send first frame before queued hints:
```
event: ready
id: <streamEpoch>:<hintSequence>
data: {"protocol":1,"appId":"tabby-rush","streamEpoch":"UUID","baselineAcceptanceOrdinal":"41","baselineHintSequence":"58","serverNow":"RFC3339","replaySupported":false}
```
`announcement` hint:
```
event: announcement
id: <streamEpoch>:<hintSequence>
data: {"appId":"tabby-rush","messageId":"UUID","acceptanceEpoch":"UUID","acceptanceOrdinal":"42","acceptedAt":"RFC3339","expiresAt":"RFC3339","emittedAt":"RFC3339","liveEligible":true}
```
`read-state` hint data `{appId,messageId}`; emitted after canonical read mutation, never OS alert. `reconcile` data `{appId,reason:"lagged"|"periodic"}`; no content. Server liveEligible only for announcement accepted in current epoch and emitted within120s of acceptance; this age check uses **server** time. Old worker recovery and delayed retry hints liveEligible false. No user identity, title/body, token or unread contents in stream. Keepalive comment every15s; check JWT expiration and current DB grant before each hint/heartbeat; expiration sends no private data and closes, revoked closes; existing sockets do not inherit stale JWT role lists. On broadcast lag send reconcile then close (client silent reconnect), not ignore loss. Server shutdown closes streams before DB/client teardown. One user multiple connections supported, capped5/user; excess429.

Client algorithm:
1. Capture account generation+identity; open authenticated same-origin stream with10s connect timeout, unlimited request lifetime,45s idle timeout (keepalive15s). No redirect, no query token. Retry1s..30s jitter; auth refresh uses existing single-flight semantics, replay open at most once after TOKEN_REFRESHED;403 revocation clears state rather than refresh loops. Close/reopen by JWT expiry; all callbacks fenced.
2. Wait ready; buffer up to256 hints while loading page1/unread and reloading visible pages/detail. Baseline hydration is always silent. Overflow ->drop buffer, close and silently restart; maintain no fabricated offset recovery. Last-Event-ID accepted but ignored for replay, ready explicitly declares false.
3. Replace refreshed first-page chain (max200 cached items), reset pagination, merge canonical readAt monotonically, remove expired/unauthorized items. Buffered announcements trigger authenticated detail refresh. Only desktop may post one generic OS alert when epoch matches ready, ordinal **greater** than baseline, liveEligible true, currently authorized detail still active, and not already seen in this connection. Mark seen before native call. Read/reconcile/inbox load never toast. Android disables this path entirely.
4. The ordinal reservation-before-insert can classify a concurrent pre-baseline admission as historical; intentionally conservative silent delivery, never loss of durable inbox. Events arriving during baseline after admission baseline are buffered and may alert once after auth fetch. Reconnect resets baseline; messages accepted during disconnect and old-epoch recovery are silent catch-up. No client-wall-clock `createdAt>=connectionTime` heuristic.
5. Dedup IDs held in-memory per account+connection, max2048. On reaching cap within same connection reconnect silently (new baseline) instead of evict-and-alert historical duplicate. Buffer256; page cache200; active nav one ID; no disk content. Refresh on hint, foreground, reconnect and60s periodic timer while authenticated process active. Refresh visible pages+unread independent of new-message cursor so cross-device reads converge. Detail opened from any native callback is refetched before display, then PUT read; failed/offline read remains unacknowledged and requires explicit online retry, no read outbox.
   Cache200 is a sliding page window, not a200-message history limit: LoadNext fetches the next server cursor and evicts off-screen page data when required; preserve forward cursor continuity, allow restart from page1, and keep every unexpired server item reachable. Never silently truncate history or restart page1 in a load-next loop. Raw FCM routing tokens stay in a private server collection with restricted DB/backup access, never API responses/logs; no new token-encryption key service is required.
6. Offline screen says unavailable/stale, hides cached body/detail; cannot open in-memory content without fresh authorization. Expiry computed from serverNow anchor + monotonic elapsed time, not client wall clock, and filtered at render/timer/foreground; if trustworthy anchor unavailable, hide until refresh. Generation change/revocation clears cache, dedup, routing, pending fetches and unread; no late callback may republish. Local process destruction discards content; server history remains90days.
