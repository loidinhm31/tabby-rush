# Hierarchy and compact-deadline design contract

Status: proposed implementation contract; no code delivered. Date: 2026-10-19.

## Authority and scope
The completed validation interview confirms exactly two levels; existing tasks stay top-level, standalone or parent-capable, and may receive new children without moving/reparenting; automatic-only parent completion while children exist (all complete → complete, adding/reopening an incomplete child → active); confirmed parent+children deletion; locally observed last-child deletion preserves immediately preceding effective completion and restores manual completion; main-app-only child creation with widget/sticky Add remaining root-only; Android widget and Linux/Windows sticky whole groups with each task's own deadline date and optional time, no inheritance; matching main status rows plus parent context, not nonmatching siblings; **local atomicity + conflict review**, not coordinated cross-device groups.

These are confirmed choices, not open defaults. ISO formatting, stable existing ordering and missing-parent recovery presentation remain conservative technical choices. Advisor refinements below define the per-row conflict/replay consequences without strengthening the cross-device guarantee. Implementation remains pending.

## Domain and completion
- Add `parentTaskId: String?`; `null` means root. Child references immutable root identity in the same account/table. Child cannot own children; self-reference, blank/noncanonical IDs, cross-account relation and changed linkage are rejected.
- Existing tasks migrate with null linkage and remain standalone or parent-capable roots; newly created children may reference them once `ready-v3`. No conversion/moving of existing roots into children, detaching children or reassignment through edit/reapply. Explicit copy-as-new recovery creates a new identity, not a move.
- Roots and children remain ordinary independent rows with their own title, deadline, reminders, sync revision and conflict state.
- `storedCompleted` means the existing wire `completed` value. `effectiveCompleted` is a projected value, never substituted into an unrelated full-replacement save by accident.
- Child effective completion = stored child completion. Root with live applicable children = logical AND over those children's effective states. Root without children is manually completable using its resultant stored raw completion, not an older pre-children value. Aggregate from the whole snapshot, not filtered or paginated subsets.
- Keep raw and effective states distinct in store/projection contracts. Editing a parent's title/deadline while grouped preserves its raw manual field rather than persisting a derived aggregate. No parent aggregate outbox write on every child change.
- Parent with children exposes progress/automatic-state semantics, not an actionable completion checkbox. Store and surface admission reject stale/manual parent completion requests; disabled UI is not the authority.
- Existing desired-state semantics remain idempotent for ordinary rows; no write or sync for an unchanged request. Represent automatic-parent rejection explicitly, without disguising it as missing or changed; migrate exhaustive callers.
- Deleting a child re-reads the group under store mutation admission. If it was the last live child, persist parent raw completion equal to its immediately preceding effective completion, atomically with child deletion/outbox intent and account revision allocation. The childless root becomes manually completable again, subject to existing unresolved-intent/conflict admission; restoration never overrides CAS review.
- Last-child preservation is atomic against the complete locally known snapshot, not a globally ordered guarantee across offline devices. A later child arriving from another device makes the parent derived again. An unresolved last-child-preservation parent UPDATE remains reviewable and suppresses parent scheduling only on the client holding that intent, including after restart until accepted or discarded. Reapply carries preservation provenance/barrier into any new unresolved preservation intent; clicking Reapply alone does not clear suppression. This special barrier does not apply to every ordinary pending parent UPDATE. Other clients may schedule authoritative raw completion after accepted child deletes because they cannot observe this client's unresolved intent. Accepted child DELETEs are not undone.
- Explicit concurrency outcome: two devices each deleting a different one of two completed children may each observe a non-last deletion and stage no parent UPDATE. Once both deletes are accepted, the childless root uses authoritative stored manual completion, even if it differs from the earlier derived state. Do not invent a synthetic CAS conflict where none occurred or claim global preservation. A user can set the now-manual root's completion normally.
- If a preserving parent UPDATE conflicts (including unrelated concurrent parent edits), retain the submitted local intent/review state; never infer that child DELETE acceptance also accepted the parent UPDATE. Discard clears that intent's barrier and recomputes from current authoritative raw completion/surviving children, subject to independent blockers. Reapply is an explicit new intent over current base and retains the barrier while its preservation intent remains unresolved. Differing concurrent completion intentions require existing conflict review, not arbitrary automatic aggregate writes.
- Reverse partial acceptance: a preserving parent UPDATE may be accepted while the child DELETE is uncertain/conflicted. Keep the accepted raw parent update; never infer child-delete acceptance or roll back that update when the child intent is discarded. Any surviving applicable child keeps the parent derived; local submitted deletion may still suppress that child on its holding client under existing projection rules. After child-delete discard/reconciliation and restart, recompute effective completion/reminder eligibility from surviving committed/submitted state; no account-wide projection promise.
- Create child only from a root's main-app action; parent identity is visible/read-only in child editor. Main quick-add and widget/sticky Add stay root-only, even while viewing a group. No drag/drop, reparenting, grandchildren, sibling-order field, or inherited schedules.

## Deletion, uncertainty and recovery
1. Confirm group deletion with parent title and count of currently known children. At commit re-read the complete current group under admission; stage parent plus all known child deletes in one SQLite transaction with distinct revisions/operation identities. Confirmation is for the group, not a stale enumerated row list.
2. Locally submitted parent deletion immediately suppresses descendants in normal task lists, counts, navigation and committed scheduling. Confirmed remote tombstone has the same dominance. Cancel native reminders/quiet deadline selections for parent and children.
3. Remote operations remain per-row CAS with independent outcomes. The parent delete need not wait forever behind a conflicted child's queue. Keep partial/uncertain child operations visible through recovery, even though normal surfaces suppress them.
4. A parent tombstone is permanent identity evidence; preserve it through scans/restarts/migrations and fetch it as part of a complete sync snapshot. Never infer a tombstone from a missing or not-yet-scanned row. No parent-ID reuse/resurrection.
5. A late surviving child whose parent is confirmed deleted stays logically deleted. Resolve any exact frozen operation/receipt first, then enqueue a normal per-row DELETE using the confirmed child revision. Reuse existing uncertainty/conflict machinery; do not rehash frozen writes, blindly reapply edits, or silently purge ambiguous records.
6. Unknown child operations remain reviewable until resolved. Existing discard/reapply/copy-as-new workflows must enforce immutable/deleted-parent rules. Copy-as-new may deliberately create a new root only with explicit user action; never auto-promote hidden children.
7. Missing parent without tombstone: expose child in an unresolved recovery section, exclude from normal completion/count/schedule projection, do not delete or rewrite it. Complete scan or explicit user recovery resolves it. Temporary pagination absence never triggers destructive cleanup.
8. Cancel a never-sent group locally only if every involved create is provably unsent and not migrated/frozen/uncertain. Do not apply the current single-row cancellation shortcut to a group with possible remote descendants.
9. Pending local root DELETE suppression is reversible; confirmed tombstone dominance is not. A conflicted/uncertain root DELETE continues to suppress the normal group while its recovery item remains available. Reapply/discard must explain partial child outcomes.
10. If child DELETEs succeed but root DELETE conflicts, discarding the root intent removes only local suppression. Restore surviving authoritative root/children, recompute effective completion from surviving children or raw root completion if none, and never resurrect acknowledged child deletions. Reconcile reminder eligibility against existing ledger/grace/permissions after discard and restart; no implicit undo or remote rollback.

## Protocol and first-dispatch ordering
- Strict-v3 adds nullable parent identity after the frozen v2 payload fields; freeze exact bytes/schema order/presence tag/domain and compute a new fingerprint in Phase 1. DELETE remains empty data; v1/v2 preimages and uncertain identities remain unchanged.
- Backend validates the relationship on fresh child CREATE and forbids parent changes on UPDATE. Require same-user live root; do not accept another user's matching row ID. Continue exact row CAS and authorization.
- Replay/receipt matching must precede current live-parent checks: accepted child CREATE + lost response + later parent deletion must still prove the original acceptance. Child DELETE must remain possible after parent deletion.
- First child admission waits for confirmed live parent root in the current account/epoch before initial freezing/dispatch; check root evidence under the existing eligibility/mutation admission. Already-admitted frozen/`UNCERTAIN` replay never waits on renewed root liveness and never changes its preimage; authorization and identity/integrity checks still apply. Distinct parent/child rows can legally share existing push batches; a batch itself supplies no dependency or atomicity guarantee.
- Per-row validation cannot atomically prevent all child-create/root-delete races. Logical tombstone dominance and subsequent durable child cleanup are the convergence contract, not an implied Mongo multi-document transaction.
- Room 2→3 adds relationship fields to all four task-bearing tables; legacy rows default to root. Preserve outbox version/provenance and frozen payload/digest/revision/identity.
- Legacy v1→v2→v3 sequencing is explicit. New v3 hierarchy creation stays unavailable until `ready-v3`; do not queue relationships under an old protocol or silently strip them.
- Upgrade reconciles v1/v2 frozen operations using original-version receipts; not-proven, unknown-superseded and integrity-failure outcomes retain existing fail-closed distinctions. Only provably unsent/not-accepted intent receives a new v3 operation identity, over scanned base.
- Unsupported client writes are fenced at v3 publication; receipt reads/replay confirmation are not authorization to apply old writes. Migration keeps epoch/row identities, enriches only the newly introduced null relationship, and never changes legacy completed/deadline/reminder values.
- New-client ordinary v1/v2 editing remains supported while those accounts await upgrade. This is migration support, not a hierarchy fallback or deprecated API shim. Post-v3 publication is forward repair only; no downgrade or destructive restore.

## Projection, filters, ordering and counts
- One shared hierarchy evaluator produces valid grouped rows, effective states, and unresolved/deleted classifications. Separate renderer-specific models may adapt it without re-implementing business rules.
- Root order and child order each preserve current encounter order (`createdAt DESC, id DESC`); stable identity keys, child directly after parent. Use indexed grouping/lookup, not repeated per-parent full-list scans.
- Compact Active section contains incomplete roots and mixed groups with **all** children together (including completed children). Completed contains completed standalone roots and fully complete groups. Never split one group across sections.
- Main All filter shows all normal tasks in groups. Active/Completed select matching real tasks; include a parent as context when its child matches. Do not include nonmatching siblings solely because of filtering. Parent with matching own status can appear without children if none match.
- Total/active/completed metrics count each real task once using effective state; total = active + completed. Context rows never inflate filtered-match counts. Recovery/soft-hidden/deleted rows are excluded from normal totals, with separate existing recovery visibility.
- Mixed-group example: root R with active C1 and complete C2 is effectively active. Main Active shows matching R+C1, not C2; main Completed shows matching C2 plus context-only R, not C1. Compact Active shows R+C1+C2 together. Counts remain based on real effective states, not duplicated context.
- No new row cap. Keep lists scrollable. If platform constraints force truncation during implementation, use explicit group-continuation/open-app affordance; never display a child without its parent context or silently lose its only access path.

## Scheduling and account fencing
- Evaluate effective completion/deletion for persisted schedules using committed base + submitted outbox snapshot only; unsubmitted editor drafts never schedule/cancel.
- Re-evaluate parent after child create/toggle/delete, scan promotion, accepted ack, conflict discard/reapply, and contract transition. Publish/invalidate once after atomic group changes, not transient halfway states.
- Completing the last active child cancels parent reminders; reopening an incomplete child re-enables parent eligibility subject to existing ledger/grace/permission rules. Completion/linkage-only changes preserve schedule tokens and consumed occurrence identities.
- Deletion suppression applies to reminder claims, posted-notification reconciliation, quiet deadline selection, and navigation—not merely drawing rows.
- All external reads/actions/publications remain bound to current `SurfaceAccountToken(accountKey, generation)`; stale cached parent/child actions cannot mutate a new account or bypass fresh child-set checks.

## Deadline presentation
- No deadline → omit metadata. Date-only → `Due YYYY-MM-DD`. Timed → `Due YYYY-MM-DD HH:mm (captured IANA zone)`; wrap metadata as needed rather than replacing its date with an icon or relative text.
- Preserve stored calendar date/time in captured zone, not device-local reinterpretation of anchor epoch. Date-only reminder anchor is never displayed as a deadline time.
- If overdue status is shown, supplement absolute date with explicit text; derive from `now >= overdueEpochMs` and effective incompletion. Never label completed rows overdue.
- Shared pure formatting belongs with shared presentation/domain contracts so main list, widget and sticky mode cannot diverge. Keep platform copy resources/adapters in their existing layer; no broad localization migration.
- Use adaptive title+metadata layout, >=48dp controls, readable metadata, child indentation and explicit automatic parent semantics. Screen readers receive parent context and full deadline even if title ellipsizes.
- Plain absolute dates need no new periodic polling. Any added overdue decoration must use existing clock/boundary paths with lifecycle-owned refresh and native acceptance.
