## 1. Decision and scope
Extend existing SharingConfig and standard push/pull/delta only. No separate task API, strict sync restoration, invitation/notification subsystem, generic role engine, app-ID conditional, Cham-lang model migration, production deployment or live data migration. All content remains one canonical creator-owned todos row. Two-level hierarchy/no reparent remains.

Research alternatives are inputs, not open implementation choices. The concrete contracts below supersede illustrative research names. Changes to these contracts require coordinated plan revision before parallel work, not silent downstream edits.

- Policy absent: existing viewer-only behavior and wire shape remain unchanged. Policy present/version 1: fixed semantics below; not configurable arbitrary permissions.
- Validate actual schema table/field types, no overlap of relation/content tables, no childTables ambiguity, nullable same-table hierarchy field, supported version, editable allowlist excluding identity/createdAt/structural keys. Reject unsupported mappings; do not silently downgrade.
- Existing optional custom JSON fields retained, not assignee-editable unless explicitly allowed by a future reviewed config change. ## 3. Canonical identity and acknowledgement
- Wire/storage logical identity: `(appId, ownerUserId, tableName, rowId)`; account partition supplies origin/current user separately. Add optional ownerUserId to push/pull records, accepted tuples, failures and conflicts; mandatory when assignment policy is active. Hub returns trusted stored userId as ownerUserId. On push it is only a selector: resolve exact stored canonical row, then authorize. No fallback to caller-owned copy, global rowId lookup or UUID probability.
- For new owner-created tasks/relations, ownerUserId must equal authenticated actor. Existing shared writes cannot upsert missing targets. `data.id == rowId`; task parent reference is within the same stored owner namespace. Owner/identity/createdAt/parent linkage immutable after create. Only owner creates children, deletes or restores.
- Acknowledgement is exact `(ownerUserId, tableName, rowId, submittedVersion)` for the frozen operation; never infer from counts or matching pull content. Do NOT add operation-receipt service or mutationId wire protocol; local opId already identifies frozen outbox intent. Research suggestions for mutationId receipts are rejected as extra scope.
- Collaborative writes require exact assumedServerVersion equality; creates require absent row/assumed 0; new submitted version must exceed current and remain a safe positive exact integer. A CAS miss is conflict, never a fresh upsert. Preserve existing standard client-version acknowledgement meaning, not server-generated receipt semantics. Delta remains sequential push then pull, not batch atomic.
- Capable-mode checkpoint keeps `{updatedAt,id}` shape, but id is the stored unique Mongo `_id` string, not rowId; sort/filter on `(syncedAt,_id)` in the same mode. Validate checkpoint format/mode; reset to null when changing mode. This handles equal timestamps, identical IDs across owners/tables, and relation/task IDs. Legacy apps retain their existing cursor semantics.

## 4. Assignment slots and policy enforcement
- Relation data: `{id, taskId, userId}`; normal version/deleted metadata stays in sync envelope. Relation rowId and data.id MUST equal taskId. Stored relation owner MUST equal stored target owner; taskId immutable. Recipient is an existing Hub user currently eligible for this app; assignment never grants eligibility. Username lookup reuses JWT-only `/api/v1/auth/lookup?username=...`; only lookup resolves names, server independently validates recipient eligibility.
- Stable slot is therefore `(appId, ownerUserId, taskAssignees, taskId)`. Existing unique `(userId,tableName,rowId)` index in each app collection backs uniqueness, including tombstones. No redundant assignment authority in todos or competing recipient rows. First assignment is a conditional create, reassignment versioned update, unassignment tombstone, regrant update of the same slot after reading current version.
- Exempt assignment-slot tombstones from generic deleted-record cleanup. Keep stable slot version/target binding so stale owner devices cannot recreate historical grants after cleanup. Ordinary task tombstone policy otherwise unchanged. No app-wide data conversion required.
- Effective access is union of creator, direct slot and live-parent slot. Inheritance is computed, including future children; never materialize duplicate child grants. All assignee access and assignment creation for a child requires an internally verified live root parent with the same canonical owner; missing/deleted/wrong-owner parents cannot produce a direct or inherited grant. A child-only recipient lacks the parent locally because it is private, not because the parent is missing on the server. Child-only access exposes no parent content or siblings. Root grant reaches the entire live two-level group. Creator may retain orphan evidence for repair/deletion, not confer access through it.
- Only creator mutates relationships, delete/restore, structural fields or child creation. Assignees may edit only editableFields of existing accessible live rows. Protect tombstone, restore, delta, relationship and malformed/empty-data paths, not only non-deleted content updates. Do not return other recipients' relation rows merely because an actor can view a child; authoritative access metadata is sufficient.

## 5. Server transaction/fence choice
- Assignment-policy apps require transaction-capable Mongo replica set. Fail closed on unsupported topology; no fallback to unguarded read-then-write. Use disposable single-node replica set for local proof; production setup remains separately authorized.
- Add one internal document per opted-in app in `_sync_assignment_fences`: `{appId, authorizationSerial, accessRevision}` with unique appId. Revision/serial are checked integers, initially 1/0. This is an internal authorization fence, NOT strict-sync epoch/admission/receipt infrastructure.
- Each opted-in canonical content/relationship mutation runs a Mongo transaction that first writes/increments authorizationSerial on this same app guard, resolves stored ownership/live task/parent/grants and current app eligibility, performs exact-version CAS, then commits. Assignment/liveness/hierarchy/config changes that can affect visibility also increment accessRevision in that transaction. All relevant transactions share the guard so revoke and edit are serialized across service processes, not merely a process mutex. Retry only transactions aborted before commit; an unknown commit outcome must remain uncertain to the client, never blindly replay a POST.
- First-create collisions use unique-index result plus reload/conflict, not overwrite. Process records with deterministic ordering; batch remains per-record acceptance rather than a new all-record transaction promise. Validate children after their parent create is accepted, or leave the child pending for a later round. No client assumes batch ordering magically establishes parent existence.
- One app-wide guard is deliberately simple and correct for this task app; it serializes opted-in writes. Record contention in disposable smoke. If unacceptable, revise design to owner/tree guards with equally proven scan semantics before release; do not silently weaken authorization. Unrelated apps never touch this guard.
- App eligibility checked against current stored user app membership for opted-in operations, not stale JWT apps claims alone. Relationship revocation's commit-order guarantee is strict. Existing general Hub membership administration remains its own mechanism; no new auto-grant pathway. A membership-denied response is authoritative and invalidates shared access locally.

## 6. Coherent reconciliation without an access-event service
Choose revision-bound access revalidation, not durable visibility event log or long-lived database snapshot across HTTP pages.

### Envelope additions
- `collaborationVersion: 1` on standard push/pull request parts, response parts echo supported 1; missing/unsupported means no collaborative interpretation.
- Pull request `expectedAccessRevision?: integer`; pull response `accessRevision: integer` for opted-in mode.
- Pull request optional `accessChecks: [{ownerUserId, tableName, rowId}]` selects validation-only mode: response has no content rows, unchanged input checkpoint, hasMore=false, and `accessResults` matching every requested identity exactly once. Bound to 100 keys and existing 256 KiB body limit. Data scans use tables todos + taskAssignees; mixed scan/check mode rejected.
- Each access result is either `{ref, status:"accessible", capabilities:{editContent,manageAssignment,deleteTask,createChild}, hierarchyCoverage:"full-group"|"child-only"|"standalone"}` or `{ref,status:"unavailable"}`. Metadata is derived from current stored state, never client-authoritative. Do not expose private parent title, sibling IDs/counts or other recipients. Owner task tombstones remain normal authorized deleted records; unavailable is NOT proof of actual deletion.
- Error 409/code `ACCESS_REVISION_CHANGED` discards only unfinished scan/validation staging and restarts from null. Per-record `ACCESS_DENIED` means no effective read access and authorizes local invalidation; `OPERATION_FORBIDDEN` means the actor still has read access but attempted a disallowed operation/field, so reject that intent without purging accessible content. App capability mismatch HTTP 426/code `COLLABORATION_REQUIRED`. Missing/repeated/mixed-owner results reject the page. Preserve sanitized existing error handling.

### Round state machine
1. Existing offline cache remains usable under last reconciled rights while disconnected. On startup/reconnect, freeze outgoing dispatch and new shared-record publication until reconciliation; local pending edits remain separately persisted.
2. Begin null-checkpoint full scan; first page supplies revision E. Each page reads revision and visible rows in one snapshot transaction; later pages require E, same policy/config mode and account generation. Any grant/revoke/liveness change increments E and invalidates the unfinished generation. Unknown JSON and table-aware canonical keys are staged, never exposed page-by-page.
3. After terminal scan, validate the union of all staged, previously accessible, draft/outbox and displayed shared identities in bounded accessChecks batches at the same E. A disappeared row is not a tombstone. Access checks consult current database membership/grants/live structure. All checks and pages must agree on E. Private owner-created unsent tasks are not treated as missing remote shared tasks.
4. Final empty accessChecks request at E confirms the boundary even when key set is empty; then atomically promote rows plus per-key access decisions in Room. E denotes rights as of the final successful server check, not an eternal lease. Grants may change immediately afterward; every push still reauthorizes. New visibility changes after E are found on the next null scan. No claim that content pages are a database snapshot or that network transmission remotely erases cached data.
5. Full-group completion is computed only from a reconciled complete hierarchy projection. Staged/partial coverage must not trigger automatic parent changes. A future child added after the boundary is observed next round; never infer completion from a child-only subset.
6. Only after promotion/revalidation select and freeze eligible outbox entries. Push independently reauthorizes under the guard; expected revision is stale-context detection, never authority. If delta push itself changes visibility, its pull part must restart rather than apply an old E; accepted push acknowledgements remain durable even if pull fails.
7. Any failed/mixed/incomplete scan or access batch leaves previous active base/access state unchanged and outgoing shared work paused. It cannot imply deletion/revocation. Authoritative per-key unavailable/ACCESS_DENIED or whole-app membership denial suppresses affected access even if a later content scan fails.
8. Maintain a persisted account-local `accessGeneration` separate from account identity generation and server E. Authoritative invalidation advances it and cancels unfinished reconciliation. Capture it on content requests and native publication admissions; under the mutation/publication lock reject results from an older accessGeneration, even within the same account or after regrant. Fresh successful reconciliation alone restores access. Exact accepted-version metadata may still be recorded separately but cannot recreate purged payloads or intents.

## 7. Local identity, migration and interfaces
- Phase 01 freezes real shared contract types and all affected signatures before parallel implementation. Domain `CanonicalRecordRef(ownerUserId, tableName, rowId)` and task-only `TaskRef(ownerUserId,rowId)` are explicit values. Every store/action/conflict/surface/navigation/reminder identity uses TaskRef, not bare rowId. Include canonical identity in schedule/delivery suppression keys and Android intents/desktop selections. No String alias shim at final cutover.
- Keep account partition as today. Room v5 explicitly rebuilds base/outbox/draft/staging keys to canonical owner+table+row, adds relationship raw JSON and authoritative access state/revision, and retains existing base/outbox/draft separation. Store/DAO projection queries exclude unavailable identities and relationship rows from task/reminder projection.
- Existing AccountKey is a one-way origin/user hash; migration cannot reverse it. Preserve legacy rows with explicit `ownerBinding = LOCAL_ACCOUNT` and nullable ownerUserId until store initialization is given authenticated/restored AccountIdentity.userId and verifies `AccountKey.create(origin,userId)` matches the opened partition. Bind all legacy private rows and dependent keys atomically BEFORE sync/shared actions; unresolved binding remains local-only, never sent or guessed. Offline private display survives upgrade; account-auth restoration supplies owner when available. Migration/constructor contract must document this two-stage binding, not hardcode a user or lose rows.
- Do not mutate prior exported Room schemas; generate new 5.json. Register explicit 4→5 and old-version→5 paths; preserve legacy evidence losslessly and maintain account teardown protections. Test populated SQLite states, not schema text.
- Required contract operations: creator assignment desired recipient with expected slot version; canonical task mutation/access lookup; stage data pages; stage access results; atomic reconcile promotion; invalidate canonical task access; owner-binding initialization. Define typed results for missing/access denied/version conflict, not generic throw-and-retry. Actual phase owns implementation, not a mock/no-op bridge.

## 8. Native behavior, retention and privacy
- Creator sees optional username assignment picker, current direct assignee and inherited indicator; recipient sees shared content controls but no assignment/delete/add-child controls. Assignment save is independent versioned relationship intent; initial assignment waits for owner task create acknowledgement. A simultaneous pending content edit is not copied into a relationship payload.
- Child-only task is a real flat/partial-hierarchy item marked shared child without synthetic parent/title. Existing-child edits may proceed with trusted canonical/access metadata despite missing local parent; new child creation still requires creator and live parent. Full-group users keep existing automatic parent completion behavior; no partial-group writes.
- Widgets/sticky/reminder actions re-resolve TaskRef/current account generation/current reconciled rights at admission and immediately before mutation/publication. On reconciled access loss, remove active task projection, cancel reminder ledger/scheduled work/notifications, blank or refresh widgets and sticky rows; existing leave cancellation barriers still apply. No second cached task store and no new assignment alerts.
- Privacy decision: after authoritative shared access loss, purge revoked remote JSON/title/deadline/assignee data and unsent shared draft/outbox payloads from active/review storage; retain only canonical identity, local opId, base/submitted version, timestamps and reason as non-replayable content-free evidence. No automatic replay after regrant. Surface a generic notice that unsent changes were not delivered. This intentionally prioritizes revoked-content privacy over recovery of unsent collaborative edits; no new encrypted quarantine subsystem.
- Do not purge unrelated owner-private tasks or existing private legacy archives. Delete content-free access-loss evidence on explicit review dismissal or account removal; no background retention system needed. Regrant hydrates original live canonical task/slot and fresh state, never resurrects old intents or locally marks the task deleted.

## 9. Compatibility and rollout boundary
- Entire sync request for an assignment-policy app without collaborationVersion=1 is rejected BEFORE mutation/pull; do not attempt unsafe private-only downgrade for an old client. Existing non-opted-in apps remain byte/behavior-compatible viewer-only.
- New clients talking to old/non-enabled servers remain current private mode; previously shared cache/outbox cannot be treated as caller-owned when capability disappears. Hide shared active state and pause shared dispatch with an actionable upgrade/configuration error. No schemaVersion threshold as gate.
- Implement server enforcement before enabling native assignment controls. Land capability-aware clients, prove both platforms, configure disposable/local app, and run hostile API plus native/offline acceptance. User confirmed the app-wide old-client online cutoff2026-10-21; preserve it in compatibility messaging and upgrade requirements, not as an unresolved policy choice. Operational enablement still requires separate authorization; do not change a real app registration in this planning task.
- Enablement/disablement of policy with existing assignment data is not an ordinary silent schema toggle: fail closed unless a separately authorized quiesced compatibility procedure preserves access state. No automatic downgrade to viewer sharing.
