## Critical / Blockers

**B1 [CONFIRMED] Credential disclosure via parse-error messages.** `hub-auth-client.kt` (all six `MALFORMED_*` catches) embeds `e.message` in `SafeError`. kotlinx `JsonDecodingException` appends `JSON input: <body>`. Probe (temp test, since deleted) on login body with `refreshToken:12345` yielded `...JSON input: {"userId":"u1","accessToken":"SECRET-ACCESS-TOKEN-ABCDEF",...}` inside `SafeError.message`. Exposure across the safe-error boundary is proven; an actual log/UI sink is not shown. Fix: constant messages (`"Malformed login response"`), never interpolate `e.message`; add regression test asserting no token/snippet appears in any `SafeError`. Same class: `hub-auth-session.kt` L158 `vaultEx.message`, `REFRESH_EXCEPTION e.message` (single-flight L104), `authorizedRequest` L415/L435 forward `error.message`; `sanitizeErrorMessage` redacts no secrets and only runs on 400 bodies / network messages.

**B2 [SOURCE] Logout vs in-flight refresh can resurrect credentials on disk.** `single-flight-refresh.kt` checks `isCurrentGeneration` then calls `vault.store` outside `sessionMutex` (check at L72, store at L82). `logout()` bumps generation and `vault.clear` under `sessionMutex`, but the leader's store is not serialized with it, and `AndroidKeystoreVault` has no mutex. Interleaving: fence passes -> logout clears file+key -> leader `store` recreates key+file for logged-out account. A check-before-suspending-write is not atomic. Fix: perform generation re-check + `vault.store` inside the same critical section as logout/quiesce (e.g. session passes a `persist` lambda executed under `sessionMutex`, or vault-level per-account `Mutex` + generation passed to the store). Need barrier-based test.

**B3 [SOURCE] Frozen-contract deviation: persistence failure after successful refresh.** Contract (plan step 4, contracts.md L25): successor retained in memory for persistence retry, background paused, restart -> ReauthRequired. Impl: coordinator returns `Failure(CREDENTIAL_PERSISTENCE_FAILED)` (`SafeError.Internal`); `HubAuthSession.refresh` discards the successor, keeps the *consumed* old refresh token in `inMemoryBundle`, and leaves state `AUTHENTICATED` (only `Unauthorized` flips to REAUTH). Next refresh replays the consumed token -> 401 -> reauth loop risk. Also: only `Unauthorized` refresh failures set `REAUTH_REQUIRED` in `refresh()`, while contract says *any* failure after dispatch (404/500/transport) is conservative reauth; `authorizedRequest` does set REAUTH on any refresh failure -> the two paths disagree.

**B4 [CONFIRMED] Android instrumented test cannot compile.** `android-keystore-vault-test.kt` L47-ish `testClearDeletesFileAndAlias` calls `assertFalse(file.exists())`; only a private two-arg `assertFalse(condition, message)` exists and `org.junit.Assert.assertFalse` is not imported. Also `shared/build.gradle.kts` declares no `androidx.test:core`, `androidx.test.ext:junit`, `androidx.test:runner`, or junit for the instrumented source set (file owned by phase 02/07; flag to owner). Android sources remain uncompiled (no SDK on host).

**B5 [SOURCE] State written without generation fence after awaits.** `checkAccess`/`handleMeAccessEvaluation` (L309), `authorizedRequest` (L409-453), `requestAccess` set `_state` after network awaits with no `currentGeneration` check -> stale reply after `logout()`/`quiesce()` can flip state back to AUTHENTICATED/ACCESS_PENDING/REAUTH_REQUIRED with null identity. Plan step 6 ("generation fences prevent stale responses") only holds for refresh/login/register. `currentGeneration` is a plain `var`, read unsynchronised from `isCurrentGeneration` lambda (no `@Volatile`; JVM visibility not guaranteed).

## High

- **H1 [SOURCE] Coordinator not keyed by account/generation.** `inFlightDeferred` is global; a caller with a newer generation/other account that joins an old leader (after leader's fence check, before `finally`) receives the old account's `CredentialBundle`, and `refresh()` writes it to `inMemoryBundle` for the new generation. Narrow window; impact = wrong-account tokens in memory (not persisted to new account's vault). Key flights by `(accountKey, generation)`.
- **H2 [SOURCE] Stale refresh token replay.** Caller captures `bundle.refreshToken` before the call; `inMemoryBundle` updated only *after* coordinator returns. A caller that read the old bundle and arrives after the leader clears `inFlightDeferred` becomes a new leader with the consumed rotating token -> false 401 -> `REAUTH_REQUIRED`. Fix: leader re-reads bundle inside the flight / compare-and-skip when stored token != captured token.
- **H3 [SOURCE] CancellationException swallowed.** `executeRaw` (`catch (e: Exception)`), coordinator leader (`catch (e: Exception)`), all `bodyAsText` catches convert cancellation into `Network`/`REFRESH_EXCEPTION` failures; cancelled leader returns a value instead of propagating. Hang risk is narrower than first assumed: `finally { mutex.withLock }` only throws if the mutex is contended at that instant; then `inFlightDeferred` stays set and `deferred` is never completed -> followers wait forever and later refreshes join the dead flight. Cleanup should use `withContext(NonCancellable)`, complete the deferred in `finally`, rethrow `CancellationException`. Add test: cancel leader with followers waiting; followers terminate; next refresh works.
- **H4 [CONFIRMED by reading] DTO/`ApiResult` `toString` leaks.** `LoginRequest`, `RegisterRequest`, `RefreshRequest`, `RegisterResponse`, `LoginResponse`, `RefreshResponse` are plain `data class`es: `toString()` prints password/tokens (`ApiResult.Success(loginResponse).toString()` too). `CredentialBundle` is redacted but DTOs bypass it. Treated as redaction defect, no sink demonstrated. Override `toString` or avoid data classes for secret-bearing DTOs.
- **H5 [SOURCE] `logout()` swallows `vault.clear` failure** and reports success; credentials may persist while UI shows logged out. Also `AndroidKeystoreVault.clear` ignores `File.delete()` return and sets `READY` unconditionally (even when another account's status was CORRUPT/LOCKED; `_status` is global, non-volatile).
- **H6 [SOURCE] Frozen interface gaps.** `AuthSession` lacks `authorizedRequest`/`quiesce`/`clearLocalCredentials` (contracts.md L81 lists them); Phase 05 must depend on concrete `HubAuthSession`. `AuthorizationUnresolved` outcome (valid /me + grant + continuing 401) not implemented: `authorizedRequest` always returns `TOKEN_REFRESHED` after refresh+/me and never evaluates a second attempt. Interface changes belong to the frozen-contract owner; report, do not patch here.
- **H7 [SOURCE] `requestAccess` deviates from plan step 4.** On any POST failure (400 validation, 429, network) it returns `Success(latest)` from the own list, masking the real failure and possibly returning an old `rejected` request as success; no bounded `/me` diagnosis; no refresh-on-/me-401. Also `authorizedRequest` does not refuse when state != AUTHENTICATED (ACCESS_PENDING/REAUTH_REQUIRED can still invoke `block`, i.e. strict sync), contradicting "pending/rejected/no grant prohibits bootstrap/sync".
- **H8 [SOURCE] Keystore vault concurrency/IO.** No mutex: concurrent `store` calls share one `.vault.tmp` (interleaved writes then atomic move of a corrupted file); `store` vs `clear` races (B2). Blocking file IO/`fsync`/Keystore calls run on caller dispatcher (coordinator calls `store` in `NonCancellable` on whatever thread; may be Main) - use `Dispatchers.IO`.

## Medium

- `AndroidKeystoreVault.load` calls `getOrCreateSecretKey`: after backup-restore/key loss it mints a fresh key then reports `CORRUPT` (indistinguishable from tamper) and leaves a stray key. `load` should never create keys; map missing alias to a distinct state. All `load` exceptions (incl. transient `KeyStoreException`/`ProviderException`) map to `CORRUPT`; should be `UNAVAILABLE`/`LOCKED` unless `AEADBadTagException`/format error.
- Login/register failure sets `UNAUTHENTICATED` while previous account's identity/bundle remain populated (inconsistent). Vault `status` not checked before network login; login can succeed server-side then fail `VAULT_WRITE_FAILED`.
- `restoreSession` does not verify `key == AccountKey.create(origin, identity.userId)`; does not catch `vault.load` exceptions; does not bump generation.
- `onCredentialPersistenceFailed` (suspend, receives raw bundle) is invoked while holding `sessionMutex` (login path) - re-entrancy deadlock if callback touches session; default no-op silently drops the recovery signal.
- `DUAL_AUTH_STRICT` with `accessToken == null` still sends `X-API-Key` without bearer; `BEARER_ONLY` with null token sends no auth header silently. Should fail locally.
- Redirects: `followRedirects=false` (client) + OkHttp `followRedirects(false)` is correct; a 3xx maps to generic `CLIENT_ERROR`. Java engine: no explicit no-redirect; relying on Ktor Java engine default (not verified). No redirect test (AUTH_ACCEPT_06 untested).
- 400 body (`sanitizeErrorMessage`) is surfaced as `Validation.message`; server may echo submitted email/password fragments. Plan step 3 says never display raw bodies/parse English text.
- DRY/KISS: six near-identical `when` blocks + three duplicated `Json{}` configs in client/http-client; collapse to one `executeJson<T>` helper. `FakeCredentialVault` lives in `single-flight-refresh-test.kt` but is used by session test; `TestHttpEngine` in client test.
- `hub-auth-session.kt` 510 LOC, `hub-http-client.kt` mixes routing/transport/error mapping; modularize (docs.maxLoc rule is for docs, but file >200-LOC convention).
- `HubAuthClient.register` does not apply `HubAuthValidation` (AUTH_ACCEPT_07 claims byte-length validation); `HubAuthSession.close` does not quiesce.
- Android: stores `Context` (use `applicationContext`); `androidx.security.crypto` dependency present in `shared/build.gradle.kts` although plan forbids deprecated encrypted prefs (unused).
- Explicit caller-supplied GCM nonce with `setRandomizedEncryptionRequired(false)`: valid (96-bit random per write, per-account key) but riskier than letting Keystore generate the IV (`cipher.iv`); KISS/safety suggestion. Class doc says "hardware-backed": not assured; emulator proves nothing about TEE/StrongBox, yet `auth-acceptance.md` §1 claims tests prove "hardware-backed key generation".
